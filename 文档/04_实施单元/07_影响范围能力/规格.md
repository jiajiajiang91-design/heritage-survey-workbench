# 影响范围能力 · 规格

补上技术架构 5.4 定义而代码里缺失的一件事：数据改了之后，程序要能说出哪些下游内容因此失效。目前依赖图在 schema 里有一个字段但永远是空数组，没有任何遍历它的代码。

## 一、依据

- 架构定义：`../../02_技术/01_技术架构.md` 第 5.4 节。依赖边的基本路径为 `证据 → 事实或决定 → 几何约束 → GeometryRevision → ViewGeometry → DrawingIR → Artifact → CheckRun → Delivery`；同节原文写明数据变化后 `ImpactService` 只遍历对应下游边，旧成果不改写，系统追加新的有效性评估，已交付或已签发版本始终保留
- 需求：核心 PRD 价值点 1（改一处数据受影响成果同步失效）、价值点 2（退回时只重做受影响部分）、用户故事 P1；功能 F01（任务要求变更时给出受影响成果清单）、F09（每个方案给出证据与影响范围）、F12（样式变更使受影响图纸失效）、F17（退回一项只使受影响内容失效）
- 动作口径：`../04_第三代动作四项/规格.md` 第三节第 1 条。退回重做与变更任务参数两条要先展示影响范围，且影响范围由程序算不由模型说
- 待落位记录：`../../05_验证证据/14_界面重做/缺口与疑点裁决记录.md` 第六节第 3 条。修改历史的影响行在 v4 上标为未落位，理由是影响范围能力属本单元尚未实现，P03 当前显示的是真实写入集而不是影响范围

## 二、现状测量

开工前清点，四条都可复核：

**依赖边字段是空的。** `ProjectSnapshotSchema.dependencyEdges` 定义了七种 `dependencyType`，但全仓库只有三处写它，三处写的都是 `[]`：`packages/application/src/project-command-service.ts` 建项目时、`packages/infrastructure/src/demo-project-package-converter.ts` 转演示包时、以及各测试的夹具。没有一处读它。三个演示包里依赖边都是 0 条。

**没有 ImpactService。** 架构里点名的这个服务在代码里不存在，`packages/application` 下没有对应文件。

**`impactRefs` 是手写的。** `Issue` 与 `Decision` 上有 `impactRefs` 字段，三个演示包的 13 条问题全部带值，但那些值来自演示定义里逐条手写，不是算出来的。真实项目里没有人会手写这个。

**依赖关系其实已经在记录里了。** 下游记录都带着指回上游的字段：`ArtifactRecord.geometryRevisionId` 与 `sourceRefs`、`CheckRun.artifactRefs` 与 `geometryRevisionId`、`DeliveryEvaluation` 的三组引用、`DeliveryDraft.evaluationId`、`GeometryRevision.geometrySpecId`、`ProjectGeometryObject.factRefs` 与 `evidenceRefs`、`FactEnvelope.evidenceRefs`、`Observation.evidenceRefs`、`MeasurementRecord.originalEvidenceRef`、`Relation.evidenceRefs`。

**成果、检查、交付不在快照里。** `ProjectSnapshot` 只到几何版本为止，`artifacts`、`checkRuns`、`deliveryEvaluations`、`deliveries` 存在项目包的顶层，工作台里是四个独立的 state 数组。因此算影响的入参不能只给快照。

## 三、开工前在真实数据上跑过一遍

七类连接逐条在三个演示包上验过，不是照着 schema 推的。结果有四件事必须先写进规格，否则实现出来的影响范围会是错的且看不出来。

**一、`factRefs` 存的是两种东西。** dai-loy 的几何对象 `factRefs` 存真实事实 id，41 条全部命中。高都与 t0b 存的是 `archetype:qing-gongcheng-zuofa:terraceHeight` 这类形制参数引用，1131 条与 1258 条一条都不命中事实。产生这类引用的是 `packages/infrastructure/src/demo-library/archetype-to-form.ts`。两种都是对的：前者的几何来自实测事实，后者来自形制推算。把 `factRefs` 一律当事实 id 处理，高都与 t0b 的事实到几何的边就全是零。

**二、形制推算这一段链路没有留痕。** 高都的事实里有间数、柱材、前廊做法这些，几何显然依赖它们，但几何对象引用的是 `archetype:` 合成字符串，不是产出该形制参数的 `ArchetypeSpec` 记录 id，而 `ArchetypeSpec` 本身也不在快照里。因此事实到形制参数到几何这条链在数据里断了一节，改一条间数算不出模型受影响。这是数据模型的缺口，不是遍历算法的问题，本单元不补这一节链路，但必须让算出来的结果说明自己算不全。

**三、t0b 有 1258 条指向包外的引用。** 形如 `demo:v3-entity:<uuid>`，是从 v3 转换时保留的原始构件 id，包里没有对应记录。它们属于真正无法解析的引用，要计数显示，不能丢。

**四、从资料出发的链是通的。** 三个包各改第一条资料，闭包分别是 33、35、74 条，都覆盖事实、几何规格、几何版本、成果、检查、交付评估、交付草案七类。这条是本单元最主要的可用路径。

从事实出发要看是哪条事实：dai-loy 的 12 条事实里只有 6 条被几何引用（`documentedDimension.*` 那组），另外 6 条没有下游，闭包为空是正确结果不是漏算。

## 四、用户故事

作为成果生产方，我改一处尺寸之后能立刻看到哪些图纸、检查和交付草案因此不能再用，以便于不去猜要重做什么，也不整批返工。

作为项目负责人，我在改任务参数之前先看到这次改动会作废什么，以便于在动手前判断代价，而不是改完才发现整套图要重出。

作为复核人员，我在修改历史里看到每次写入影响到什么，以便于判断某次改动之后的成果还能不能用。

## 五、范围

### 5.1 依赖图按推导得出，不另存一份

依赖边从记录已有的引用字段推导，不新增写入路径，不做数据迁移。

理由是另存一份就有两个真相。记录里的 `geometryRevisionId` 是权威的，另存的边只是它的副本，两者一旦不同步，按边算出来的影响范围就是错的，而且错得看不出来。修改历史模块顶部已经为同类问题写过同样的判断，本单元沿用。

`dependencyEdges` 字段保留在 schema 里不动。删它要改快照版本号并动到导入导出与三个演示包，收益只是去掉一个空数组。字段旁加注释写明它已由推导取代，并加一条测试锁住不许再往里写。

### 5.2 推导规则

七类边，每类的出处如下。表里的字段名就是实现要读的字段，不允许凭猜增补。

| 边类型 | 从哪推 | 方向 |
|---|---|---|
| `evidenceToFact` | `FactEnvelope.evidenceRefs`、`Observation.evidenceRefs`、`MeasurementRecord.originalEvidenceRef`、`Relation.evidenceRefs` | 资料 → 事实、现状、实测、关系 |
| `factToConstraint` | `ProjectGeometryObject.factRefs` 与 `evidenceRefs` | 事实与资料 → 几何规格。`factRefs` 里以 `archetype:` 开头的不是事实 id，是形制参数引用，单独归类不建边 |
| `constraintToGeometry` | `GeometryRevision.geometrySpecId` | 几何规格 → 几何版本 |
| `geometryToView` | `ArtifactRecord.geometryRevisionId` | 几何版本 → 成果 |
| `viewToArtifact` | `ArtifactRecord.sourceRefs`、`ArtifactRecord.requirementMatrixId` | 出图依据与任务要求 → 成果 |
| `artifactToCheck` | `CheckRun.artifactRefs`、`CheckRun.geometryRevisionId` | 成果与几何版本 → 检查 |
| `checkToDelivery` | `DeliveryEvaluation` 的 `artifactRefs`、`checkRunRefs`、`geometryRevisionId`；`DeliveryDraft.evaluationId` 与 `artifactRefs` | 检查与成果 → 交付评估与草案 |

### 5.3 ImpactService 的职责

输入一组变更引用，输出下游闭包，按记录类型分组，每组给出条数与可读名称。

三条硬要求，都来自架构 5.4 原文：

- 只遍历下游边。改一份资料不影响另一份资料，也不影响它的上游
- 不改写旧记录。输出是一份评估结果，不去修改已有成果的状态字段
- 已交付或已签发版本始终保留。闭包里出现这类记录时标出来但不标为失效

### 5.4 两处使用

**修改历史每条带影响行。** 现在每条显示时间、操作人、动作、改了哪些对象、为什么改，再加一行这次写入影响到什么。写入集与影响范围是两件事，界面上要分得开：写入集是这条命令自己动了什么，影响范围是因此失效的下游。

**变更任务参数先展示影响。** 这个动作本身属单元 08，本单元只提供它调用的接口与返回结构，并保证接口在没有下游时返回空而不是报错。

## 六、业务规则

**影响范围由程序算。** 模型只负责理解用户想改什么，算影响是程序的事。助手动作层拿到的是程序算出的结果，不允许模型生成影响清单。

**算不出来要说算不出来。** 引用指向的记录在快照里找不到时，计为一条无法解析的引用并显示出来，不静默丢弃。丢弃会让影响范围显得比实际小，而这正是用户据以判断的数字。

**空影响是合法结果。** 一份刚上传还没被任何事实引用的资料，改它的影响范围就是空。界面显示无下游受影响，不显示未计算。

**形制推算这一段算不全，结果要自己说出来。** 项目里存在 `archetype:` 引用的几何对象时，从事实出发的影响范围必然偏小，因为事实到形制参数到几何这条链在数据里断了一节。返回结构里带一项覆盖缺口说明，界面据此提示这次算的不全。宁可显示算不全，不显示一个偏小的数字。

**已交付版本不标失效。** 闭包里遇到 `status` 为已交付或已签发的记录，列出但标注为已交付版本保留，不计入失效数。当前产品只有代理交付草案，这条先按字段判断实现，等正式签发能力具备后不必再改。

## 七、界面要求

修改历史的影响行在 v4 上还没有画。本单元实现能力并产出真实数据之后，v4 的 P03 屏要补上这一行，再由单元 08 按 v4 实现。顺序不能反：先有能算出来的数据，才画得出不是编的界面。

影响行的文案形态待 v4 定稿，本单元不定。本单元只保证接口返回的数据够画：分组名、条数、每条的可读名称、无法解析的引用数。

## 八、不做

- 不做正式签发与签名失效。架构第 662 行与第 673 行定义的签名失效规则属私有部署，本产品当前没有真实签名记录
- 不改写任何已有记录的状态字段。本单元只算不改
- 不做退回重做、变更任务参数两个动作本身，它们属单元 08
- 不删 `dependencyEdges` 字段，不动快照版本号
- 不做影响范围的可视化图形。界面上是分组清单，不是依赖关系图
- 不补形制推算的链路留痕。让 `ArchetypeSpec` 进快照、让几何对象引用它的记录 id 而不是合成字符串，是数据模型改动，牵动几何管线与三个演示包，另排单元。本单元只把这条缺口显式报出来
